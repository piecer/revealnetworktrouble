## 확인된 결함

### P1-01 요청 전체 동시 실행량이 무제한이다

- 위치: `backend/diagnostic/runner.go:76-95`, `backend/api/server.go:50-74`
- 경로: 인증되지 않은 동시 POST → 요청마다 최대 20 goroutine → TCP/HTTP/외부 프로세스 생성.
- 영향: 원격 요청 수에 비례해 고루틴·소켓·`traceroute` 자식 프로세스가 증가하여 서비스/호스트 자원 고갈 가능.
- 수정: 전역 report admission semaphore와 명시적 429/503 계약, 활성 작업이 용량에서 빠지지 않는 취소·종료 처리.
- 회귀: barrier checker로 한도까지 점유 후 다음 요청 거절과 완료/취소 뒤 용량 회복 검증.

### P1-02 기본 배포 경계가 내부망 진단 능력을 공개한다

- 위치: `cmd/checknetwork-api/main.go:26-34`, `compose.yaml:4-8`, 각 network checker.
- 경로: 전체 인터페이스 bind + 인증 없음 + 사용자 주소를 DNS/TCP/HTTP/서비스/traceroute sink에 전달.
- 영향: 공개된 인스턴스가 내부 포트 스캔, HTTP redirect 기반 사설 주소 접근, 경로 정보 노출에 악용 가능.
- 수정: 기본 loopback bind, `trusted-local`/`public` 배포 모드, public 모드의 인증·rate limit·사설/메타데이터 대역 및 redirect 재검사. 사내 진단이라는 목적 때문에 private 접근을 무조건 제거하지 않고 정책으로 분리.
- 회귀: loopback 기본값, public 모드 direct/redirect DNS rebinding 경계, trusted 모드 사설 진단 허용 검증.

### P1-03 유효 API 작업 시간과 HTTP 서버 timeout이 모순된다

- 위치: `backend/diagnostic/runner.go:82-91`, `cmd/checknetwork-api/main.go:31-34`.
- 근거: traceroute 최대 예산은 `30초 × 10회 = 300초`지만 서버 `WriteTimeout`은 35초다.
- 영향: 유효한 요청이 서버 내부에서 계속 실행되면서 클라이언트에는 결과가 전달되지 않는다.
- 수정: 하나의 계산된 report budget을 validator·runner·HTTP server·client가 공유하고, 각 attempt timeout을 독립 적용.
- 회귀: 최대 설정의 handler lifecycle 및 attempt별 timeout 재설정 검증.

### P1-04 HTTPS 검사가 HTTPS→HTTP downgrade를 정상으로 판정한다

- 위치: `backend/diagnostic/http.go:39-60,77-90`.
- 경로: 최초 URL만 https 확인 → redirect는 횟수만 제한 → 최종 HTTP 200이면 healthy.
- 영향: TLS 정상성 검사가 평문 응답을 정상으로 오인한다.
- 수정: redirect마다 https 유지, 최종 `resp.TLS` 존재를 검증하고 안정적 오류 코드를 제공.
- 회귀: 로컬 TLS 서버가 HTTP 서버로 redirect하는 fixture가 downgrade 오류를 반환하는지 검증.

### P2-01 Web 재실행·실패 시 이전 결과가 현재 결과처럼 남는다

- 위치: `frontend/app.js:763-830`.
- 영향: A 성공 후 B 로딩/실패 시 A의 완료 배너·표·지도와 B 오류가 동시에 표시되어 잘못된 판단을 유도한다.
- 수정: request owner/input signature, idle/loading/ready/error/cancelled 상태, AbortController, 이전 결과 명시 또는 제거.
- 회귀: A-success → B-pending/failure, A-late → B-success deferred response 테스트.

## 제품 여정 갭

현재 흐름은 “검사 종류/주소 입력 → raw 측정 → JSON”이다. 목표 흐름은 다음이어야 한다.

1. 증상/영향/발생 범위 입력 또는 목적 기반 preset
2. 환경과 vantage가 기록된 자동 검사 구성
3. 원인 후보를 위협/장애 확률이 아닌 관측 근거로 분리
4. 각 후보의 evidence와 “왜 더 강하게 말할 수 없는지” 표시
5. 안전한 다음 확인 단계와 에스컬레이션 조건
6. 사람이 읽는 redacted 공유 보고서와 원본 JSON 분리
7. 반복 이력/baseline 비교 후 회복 확인

현재 telemetry로 DNS 해석 여부, TCP 연결, HTTP status, 성공 TLS 세부, 반복 traceroute 도달/분기/50ms 지연 증가는 판정 가능하다. 실제 packet loss/jitter/bandwidth, 클라이언트 Wi-Fi·VPN·proxy, 분산 vantage, 장애 지속성은 추가 수집 전에는 단정할 수 없다.
